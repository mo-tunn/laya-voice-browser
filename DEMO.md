# voice-browser demo — local laya-browser

This walkthrough shows the hybrid decision architecture: deterministic code handles commands that can be resolved exactly, while the local browser-specialized Laya checkpoint handles ambiguous page-local UI decisions.

## Setup

From PowerShell:

```powershell
.\run.ps1
```

Open the control room at **http://localhost:8787** in Chrome or Edge and enable the microphone. A separate Chromium window is controlled by Playwright.

The header should show:

```text
model: cklxx/laya-browser
cost: $0
```

## 1. Deterministic global command

Say:

> go to wikipedia

Point out that this command does not need model inference. The destination is a known closed-set site and code owns the final URL.

Then say:

> scroll down a bit

Scroll direction and amount are also deterministic.

## 2. Verbatim search payload

Say:

> search for alan turing

The query string is extracted from the transcript in code. It is never generated by the model.

If the current page has a search box, code uses that field; otherwise it constructs a deterministic search URL.

## 3. Page-local semantic target

Navigate to a page with several links and say something like:

> open the documentation

This is where the local browser model is useful. The Node adapter sends a compact observation:

- visible page text;
- a bounded list of actions such as CLICK / TYPE_TEXT / SELECT;
- element labels and roles;
- the spoken command as the goal;
- recent browser-action history.

The checkpoint returns an operation and target probabilities. Playwright still performs the action.

## 4. Explicit target filtering

On a search-results page say:

> click the first result

Ordinal result references are resolved deterministically before model inference, so unrelated page chrome does not compete with the intended result.

Likewise, a strong explicit label such as:

> click the github link

is matched against visible labels/hrefs before trusting a fuzzy model target.

## 5. Typing without model-generated text

Say:

> type hello world into the search box

The browser model may select the correct field, but the text `hello world` comes verbatim from the transcript. The model does not generate it.

## 6. Destructive-action gate

On a test checkout page say:

> click place order

The target can be selected, but policy code classifies the action as destructive and asks for spoken confirmation before execution.

Then say:

> confirm

The pending action is executed only after that confirmation.

## 7. Ambiguity without hallucination

Ask for a target that is not present:

> click sign in

The adapter checks whether the chosen model element actually overlaps the explicit requested target. If it does not, the target is rejected rather than clicking an unrelated element.

When several candidates remain plausible, the browser shows numbered choices. Saying:

> two

is parsed by code and does not call the model again.

## 8. Context-aware correction

After clicking a result, say:

> no, not that one

Recent action history lets policy reverse the last action.

Or say:

> no, the other one

The previous target is excluded and the next plausible target can be selected.

## What to highlight

The important boundary is not “AI controls the browser.” It is:

```text
speech
  -> deterministic parsing/filtering
  -> small browser action space
  -> local laya-browser only where semantic judgment is useful
  -> deterministic safety policy
  -> Playwright execution
```

This is why the model does not have to reason over raw HTML, invent URLs, invent typed text, or understand every browser command at once.
